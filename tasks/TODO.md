## 마켓형 플러그인 전환 과제

- [ ] **외부 플러그인 실행 모델 결정**: 메인 앱 컨텍스트에서 JS를 직접 `import()`할지, iframe/Electron `<webview>`로 격리 실행할지 결정한다. 생태계형 마켓을 목표로 하면 기본값은 격리 실행이어야 한다.
- [ ] **플러그인 manifest 표준화**: `id`, `name`, `version`, `entry`, `icon`, `defaultSize`, `minSize`, `permissions`, `apiVersion` 필드를 정의한다.
- [ ] **권한 모델 설계**: `network`, `storage`, `notification`, `openExternal`, `clipboard` 같은 권한을 manifest에 선언하고 설치 전에 사용자에게 표시한다.
- [ ] **플러그인 bridge API 설계**: 외부 플러그인이 앱 기능을 직접 만지지 못하게 하고 `lifedash.storage`, `lifedash.http`, `lifedash.notify`, `lifedash.ui` 같은 제한 API만 제공한다.
- [ ] **플러그인별 저장소 격리**: `pluginId`와 설치 인스턴스를 기준으로 namespace를 분리하고, 다른 플러그인 데이터 접근을 차단한다.
- [ ] **로컬 설치소 구현**: 마켓 연동 전 단계로 로컬 디렉터리 또는 zip 패키지를 설치하고 manifest를 읽어 대시보드에 표시하는 로더를 만든다.
- [ ] **마켓 API 계약 정의**: 플러그인 목록, 상세 정보, 다운로드 URL, 버전, 권한, 서명 정보를 내려주는 API 스키마를 만든다.
- [ ] **서명 및 무결성 검증**: 마켓에서 받은 플러그인 패키지가 변조되지 않았는지 확인한다. 외부 개발자 생태계에서는 선택 기능이 아니라 필수 안전장치다.
- [ ] **업데이트 정책 설계**: 자동 업데이트 여부, 권한 변경 시 재승인, 호환되지 않는 `apiVersion` 처리 방식을 정한다.
- [ ] **현재 내장 플러그인과의 공존 전략**: `src/plugins` 기반 내장 플러그인과 마켓에서 설치되는 외부 플러그인을 같은 Dashboard에서 어떻게 구분하고 렌더링할지 정한다.
